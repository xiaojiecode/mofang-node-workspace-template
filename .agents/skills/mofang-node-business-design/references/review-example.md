# 假设案例：筛选候选后人工审核

本例只演示推导方法。业务假设为：能力返回候选，用户选择一部分流转，下游仅收到已流转内容。实际字段、动作名和能力必须由当前 CLI、类型和源码查证。

## 先暴露会改变结果的决策

“不选择”可能表示尚未操作，也可能表示明确放弃全部，两者不能自动等同。零结果可能允许结束，也可能需要改条件后重新发起。任务失败时是否保留已产生候选、是否允许逐项处理，同样需要业务确认。不要先生成一个 disabled 按钮再让用户困在页面。

| 条件 | 需要确定的规则 | 实现前应取得的证据 |
| --- | --- | --- |
| 能力成功，结果为空 | 如何结束或由用户发起下一次操作 | 能力空结果语义、用户决定、真实可用动作 |
| 有候选，未选择 | 保持等待还是允许明确放弃 | 候选处置契约、用户决定 |
| 部分选择 | 流转后其余候选如何处置 | 逐项流转/丢弃能力、剩余义务 |
| 业务调用结果未知 | 查询原结果或人工核对 | 原操作身份及实际查询能力 |
| 动作受理后断线 | 按 eventId 恢复结果 | 持久动作查询与固定上界列表契约 |

确认之后再把规则落实到现有字段、状态槽和动作；表中的处理方向不是预先批准的功能。

## 划清事实和显示

候选及修订、任务结果、动作 outcome 是实际事实。页面中的选择集合通常是当前视图交互状态，不应自动改成节点持久选择；如果需要跨会话保存，先讨论归属及契约。用户关闭抽屉不提交业务决定。

Project 只投影已提交事实；页面重开、Project 重算或收到订阅不重新调用筛选能力。候选已流转的快照不可编辑，冲突时保留尚合法的用户输入并说明实际变化，不静默再次提交。

## 验证所确认的规则

例如用户确认“零结果可结束、无选择保持等待”后，应验证空结果能到达结束入口，有候选但未选择不会隐式丢弃；流转一项时输出内容与来源正确，其余候选仍按确认规则处理。动作已受理后即使 nodeView 没变化，也应按 eventId 得到结果；刷新仅查询，不额外产生调用。

如果已有平台不支持某条路径，报告具体缺口并回到方案讨论，不用前端假状态或直写存储补齐。
