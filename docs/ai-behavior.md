# AI 意图路由

本模板把 AI 视为节点作者和平台操作代理。用户的自然语言先映射到一个明确的操作层级，再执行对应入口；不能把本地预览、平台保存、实例发布和真实运行合并成一个“完成”动作。

| 用户意图 | AI 行为 | 需要停下确认的边界 |
| --- | --- | --- |
| 讨论方案、审查现状 | 只读规范、源码、Schema、测试和 Git 状态，输出事实与方案 | 不修改文件，不访问外部写入接口 |
| 创建独立工程 | 使用 `init`，目标目录必须为空，生成带空 nodes/ 的工程 | 目标路径或工程名不明确时询问 |
| 在现有工程新增节点 | 先加载与任务匹配的 skill，再进入创建引导，确认业务目标、可用能力和节点边界，最后使用 `node:new` 生成骨架并实现业务 | 节点编码、能力来源、输入输出和面板渲染器不能猜测 |
| 编写或修改节点逻辑 | 先加载 `mofang-js-node`，再读取可信类型和能力双 Schema，默认本地 Mock | 输入输出、状态、人工动作、恢复和失败规则会改变行为时先确认 |
| 修改 Lit 面板 | 先加载 `mofang-lit-node`、`mofang-lit-ui` 和按需的 `lit-best-practices`，优先查询并复用内置 Lit 组件，再修改源码并本地验证 | 不把页面展示逻辑改成业务执行逻辑；只有内置组件无法满足需求时才增加自定义结构 |
| 修改 Puck 面板 | 先加载 `mofang-lowcode-node`，再运行 `lowcode guide/catalog/inspect`，使用带 revision 的语义操作并 validate/preview | 冲突必须重读并合并，不能覆盖未知组件或绑定 |
| 预览页面 | 只生成本地 Mock 预览 URL，核对实际 revision 和交互 | 不保存页面、不调用真实能力、不宣称真实链路成功 |
| 验证本地产物 | 按风险运行 typecheck、build、verify、trial 或平台 doctor | 验证通过不等于平台保存、发布或业务验收 |
| 保存目录或面板 | 读取最新身份和 revision，分别准备并执行对应保存操作 | 目录、settings、business 必须分开确认和回读 |
| 发布已有实例 | 查询实例并使用明确 scope 和 targets | 不默认 `all_instances`，不把页面发布当执行定义更新 |
| 真实调用或试跑 | 使用同环境 client profile 和明确 workspace，保留原始回执 | 必须有明确授权；未知结果先核对，不能自动重发 |
| 同步模板 | 使用 `upstream sync`，保留本地提交并普通合并 | 不自动 reset、rebase、切分支、删除业务文件或推送 |
| 恢复同步记录 | 使用 `upstream recover` 补记已完成或已撤销状态 | 不重写文件、不重新合并 |
| 删除或重置工程 | 先核对目标路径、范围和当前 Git 状态，再执行用户明确授权的破坏性操作 | 不把历史提交、AGENTS.local.md 或缓存当作恢复依据 |

## 页面效果确认

创建节点页面或调整页面结构前，先核对目标客户端的实际展示结构、已有页面和模板预览，再按下面顺序与用户确认。Puck 和 Lit 都适用；已确认的结构沿用，纯逻辑修复不重复询问。

1. 用一句大白话说明默认准备做的页面：展示哪些内容、用户能做什么。按没有开发经验的用户来讲，不要求用户理解宿主、surface、SDK 等实现概念。
2. 画一张简单示意图，完整展示展开后的节点面板，最多带上工作流画布作为背景，不包含系统左侧导航或其它应用区域。标题、状态、列表、按钮、执行信息等实际可见区域都要画出来，位置与最终布局一致；列表须画出表头、代表性行和行操作，不能只写“商品列表”。示例数据标明为示意。
3. 只问一句：“默认准备做成图里这样，需要增加、删除或调整哪些内容？”用户确认后再搭建；用户提出调整则更新示意图并确认变动部分。将确认结果留在当前任务记录中，供预览验收对照。

右侧执行信息如果实际会出现，就必须画出来，不能自行规定“默认不显示”，也不能只画低代码业务内容而漏掉客户端提供的区域。用户要求隐藏或移动某区域时，先核对当前能力；无法通过页面配置实现的，说明需要改客户端，不能在图中隐藏后声称已支持。无法核实的区域标明“待核实”，不能当成最终效果交付。

预览与交付时逐项对照已确认示意图，核对展示内容、操作和布局。若本地预览缺少客户端区域，明确说明差异；发现最终页面会多出或缺少区域时，先更新示意图向用户说明并确认，再继续交付。

## 入口选择

- `npm run init -- --dir <目录> --name <名称>` 创建独立工程。
- `npm run node:new -- --code <编码>` 在当前工程增加中性骨架；`init` 只创建空工程，不带业务节点。
- `npm run lowcode -- <动作>` 只操作本地页面包和预览。
- `npm run platform -- <参数>` 访问平台 CLI；目录和 Schema 查询默认只读。
- `npm run upstream -- sync|recover` 管理模板合并状态。

`保存页面`、`发布页面`、`采用执行定义`和`启动新运行`是四个不同动作。用户只说“发布”或“运行”时，先确认具体对象和范围。

平台 CLI 的参数由 npm 转发时使用 `npm run platform -- --profile <名称> ...`；直接调用包装器时使用 `node tooling/cli.mjs platform --profile <名称> ...`。包装器会兼容一个多余的单独 `--`，但 AI 应优先使用上面的规范形式。

## 创建节点的引导流程

用户说“创建一个节点”时，AI 不应立即生成代码或套用某个预设。先把用户的想法整理成可实现的业务目标，再进入节点作者流程。提问应使用魔方业务语言，技术名词只在执行命令或解释错误时补充说明。

### 先加载相关 skill

识别任务类型后，AI 必须先读取对应的 SKILL.md，再按技能指引调查、设计或实现；不能只根据技能名称、简介或记忆直接编写代码。同一会话已经读取且未变化的技能无需重复加载。

- 节点业务规则、状态和人工决策：先读 [mofang-node-business-design](../.agents/skills/mofang-node-business-design/SKILL.md)。
- 后台逻辑和能力接入：先读 [mofang-js-node](../.agents/skills/mofang-js-node/SKILL.md)。
- 页面信息组织和交互设计：先读 [mofang-node-ui-design](../.agents/skills/mofang-node-ui-design/SKILL.md)。
- 标准 Lit 设置或业务面板：先读 [mofang-lit-node](../.agents/skills/mofang-lit-node/SKILL.md) 和 [mofang-lit-ui](../.agents/skills/mofang-lit-ui/SKILL.md)，编写或审查 Lit 组件时同时遵循 [lit-best-practices](../.agents/skills/lit-best-practices/SKILL.md)。先查公共组件导出、参数类型和已有预览，再组合页面。
- Puck 页面：先读 [mofang-lowcode-node](../.agents/skills/mofang-lowcode-node/SKILL.md)。

相关技能尚未读取时，可以先澄清意图、核对工作区；不能开始对应的设计或实现。技能和组件选型由 AI 负责，不要求 FDE 选择或理解这些技术名称。

### 先确认用户想做什么

先判断用户是在创建新节点、修改已有节点、调试节点、配置页面，还是准备发布/运行。只有确认是创建新节点，才进入下面的引导；意图不清时先用一个简短问题澄清，不要同时追问无关细节。

### 主动收集业务信息

按实际缺口逐步提问，至少确认以下内容：

- 节点服务的使用者和要解决的业务问题；
- 节点什么时候开始工作，以及查询条件来自哪里；
- 用户需要填写或选择哪些条件；
- 节点最终要交给下游什么结果；
- 是否需要人工查看、筛选、确认或放弃；
- 零结果、调用失败、结果不确定和用户不操作时如何结束。

用户已经说明的内容不重复询问。多个合理方案会改变结果时，列出简短选项和影响，等待用户选择；不能用默认值掩盖尚未确定的业务规则。

### 先查找匹配的业务能力

用户只需要用自己的业务语言描述目标，例如“寻找热门商品”“分析某个类目的趋势”或“把筛选后的商品交给下一个节点”。AI 应先从这段描述中提取业务对象、动作和结果，再到魔方后台的业务能力目录中查找可能匹配的能力，不要求用户先知道能力名称、字段或系统内部编码。

当节点需要调用魔方业务能力时，AI 应根据用户选择的环境直接打开内置浏览器的对应后台入口，引导用户完成登录。当前已知的测试环境后台入口是 `https://dev.admin.mofang.com/`；其它环境必须使用已确认的入口，不能根据域名规则猜测。登录页面需要用户输入账号、密码或完成额外验证时，应把输入步骤交给用户接管；AI 不索要密码，不把凭据写入对话、源码或文档，也不根据手机号或管理员账号代替业务用户。仅打开页面或看到登录页不能视为登录成功，必须根据页面状态或能力读取结果确认。

用户完成后台登录后，在用户已明确授权的前提下，优先复用当前浏览器会话中的后台访问令牌，导入本机 CLI 的私有会话，再用 CLI 读取能力目录和详情，避免要求用户重复登录。导入时必须保持环境和身份一致，使用受限的标准输入或内存管道，不把令牌拼进命令行、URL、日志、对话、源码或交付文档；导入完成后只展示登录状态、环境和有效期，不展示令牌内容。浏览器会话没有可复用令牌、令牌身份不匹配或导入失败时，明确说明原因，改用正常的 CLI 登录或令牌导入流程，不能绕过身份校验。

如果内置浏览器无法打开入口、连接被拒绝或页面无法确认登录状态，明确报告具体情况，暂停依赖后台能力的步骤，并引导用户检查环境入口或完成登录；不能假设能力存在或绕过登录。

登录完成后，读取当前账号可用的业务能力列表，并根据用户目标筛选候选项。向用户列出匹配的业务能力，至少说明：

- 这项能力能解决什么业务问题；
- 需要用户提供哪些条件；
- 会返回哪些结果；
- 是否需要等待系统处理；
- 是否可能产生费用或受使用权限限制。

如果有多个能力都可能满足目标，列出它们的区别和适用场景，让用户选择；如果没有匹配能力，说明已查到的范围和缺口，再讨论是否调整目标。不能只把内部编码或一串原子能力名称直接交给用户选择。

能力列表或详情不可读取时，明确说明缺少后台权限、登录状态或能力说明，并暂停依赖该信息的实现；不能根据能力名称、旧示例或猜测的字段编写映射代码。

### 区分能力查看和能力调用

后台管理身份只用于查看能力目录和完整说明，不能代替实际业务用户调用能力。需要真实试调用或试跑时，AI 应引导用户使用同一测试环境的客户端 CLI 登录：用户输入手机号，CLI 发出验证码，用户在登录流程中输入验证码后保存客户端会话。验证码、访问令牌和刷新令牌不得写入对话、源码、日志或交付文档，也不能把后台管理员身份当作客户端用户身份。

在开始编写节点前，必须先读取所选能力的完整输入和输出说明，并确认：

- 所有必填条件、可选条件、默认值和互斥条件；
- 返回结果的实际列表位置、字段含义和空结果表示；
- 成功、业务失败、技术失败、等待中和结果未知的区别；
- 是否需要工作流上下文、是否支持分页，以及分页或继续查询所需的凭据；
- 能力是否可用、是否可能计费，以及实际调用所需的客户端身份。

如果这些信息没有完整读取，先停留在方案整理阶段，不编写字段映射、分页、重试或结果判断代码。真实试调用必须使用客户端 CLI，并保留原始回执；管理员 CLI 只做目录读取和不落库校验。

### 确认节点契约

选定能力后，用业务语言确认“输入什么、做什么、输出什么”：

- 查询条件是节点设置、上游数据，还是两者组合；
- 能力返回的内容如何转换为节点结果；
- 结果是直接交给下游，还是先由人工筛选；
- 查询提交后是否要等待结果，以及等待期间页面显示什么；
- 哪些结果可以继续，哪些结果必须人工处理或结束。

真实能力的字段、类型、状态和失败信息必须以后台读取到的实际说明为准。没有读取到完整说明时，只能整理方案，不能编写猜测性的映射代码。

### 引导设置、业务面板和示例

节点契约确认后，AI 再提出设置页面和业务面板的配置方案：

- 设置页面承载查询条件、默认值和清空语义；
- 业务面板承载结果、进度、空结果、失败原因和人工操作；
- 输出说明列出下游实际能拿到的字段和结果状态。

标准代码页面优先使用模板内置 Lit 组件、样式和交互约定。AI 应先查询现有组件是否能满足字段、卡片、表格、状态、按钮和布局需求；只有确认没有合适组件时，才编写自定义 HTML 或 CSS，并说明复用缺口和新增结构的原因。自定义结构仍需接入宿主状态、权限、动作结果和无障碍要求，不能因为页面特殊就绕过公共组件的行为约定。

用户表达不清时，先给出可修改的字段示例、输入输出示例、流程图或页面草图，再继续提问。需要真实填写和点击时，使用本地预览或节点面板验证，不依赖聊天窗口渲染任意 HTML。

### 生成和验证的边界

完成业务确认后才运行 `node:new` 或修改节点文件。实现顺序为：节点合同和执行逻辑、设置页面、业务面板、本地 Mock 与预览、类型和产物检查。目录保存、页面发布、实例采用和真实运行仍是独立动作，必须按原有规则分别确认；本地示例、Mock 或预览不能被描述成真实业务调用成功。
